## 重要：抓取时的编码陷阱

服务端对 JS 类资源返回 **`Content-Encoding: gzip`**，且内容是 **GBK** 编码：

- `http://192.168.0.203/a41.js` 不带 `Accept-Encoding` 时，传输体就是 51200 字节的
  gzip 压缩流。若直接当文本看会误判为「文件被截断成 50KB」，实际是未解压。
- 解码需先 `gzip.decompress()`，再按 **gb18030** 解码（UTF-8 会乱码）。

本目录中的文件均已解压，未再压缩。

## 结论：接口与协议**没有破坏性变动**

逐项核对下列约定，全部仍然成立（`campus_login.py` 无需改动）：

- `login_method==0` → 走 `page.path + 'login'`（即 `/drcom/login`），主认证流程未改
- `callback` 仍由 `unshift` 置于查询串首位
- 参数编码仍为 `encodeURIComponent`
- `en_md5` 分支：`upass = calcMD5(PID+upass+CALG)+CALG+PID`，且 `R2 = page.en_md5 ? 1 : ''`
- `calcMD5` 实现未变（`binl2hex(coreMD5(str2binl(str)))`，`str2binl` 仍是 `charCodeAt(i)&0xFF`）
- `PID='1'`、`CALG='12345678'` 未变
- 账号去空白 `replace(/\s+/g,'')` 未变
- `prefixAccount = accountPrefix + DDDDD + tempAccountSuffix` 未变
- `terminal_type=term.type`、`mac_type`、`business_type=term.business_type`、
  `operate="portal_login"` 均未变
- `chkstatus` / `loadConfig` 接口路径未变

## `loadConfig` 字段变化

字段总数 85 → 85，**无新增、无消失**。但三个值有变动：

| 字段 | 旧参考 | 实测 | 影响 |
|---|---|---|---|
| `page_index` | `3GozJf1788490374` | `CAyDOb1788961749` | 动态值，必须运行时获取 |
| `rcn` | `ovlCKe9f` | 每次调用都不同 | 动态值，必须运行时获取 |
| `no_filter_accandpwd` | `0` | `1` | **见下** |

其余关键字段（`enable_r3=1`、`en_md5=0`、`login_method=0`、`account_prefix=1`、
`enable_verify=0`、`ep_http_port=801` 等）均未变。

### 关于 `no_filter_accandpwd` 由 0 变 1

该字段置 1 时，页面会在**部分流程**中对 `user_account` / `user_password` 做 base64：

```js
'is_base64encode': ... ? term.no_filter_accandpwd : 0,
'user_account': ... && term.no_filter_accandpwd==1
                ? util.base64Encode(this.prefixAccount)
                : this.prefixAccount,
```

但**这段代码位于 iPad 终端的 `orientationChange_ipad` 流程**（`term.type==2` 分支），
且该 base64 分支在**旧参考 `a40.js` 中同样存在** —— 不是本次新增。

我们复刻的 `default_login` → `portal_login` 主流程（`term.type==3` PC 端）**不含**
base64，实测确认：

- `default_login` 内的 `data` 对象：明文 `DDDDD` / `upass`
- `portal_login` 内：`data.user_account = this.prefixAccount`，无 `base64Encode`
- 且本机账号为纯数字，不含特殊字符

**所以对当前使用方式无影响。** 若日后改用 iPad 终端类型，则需按该分支处理。

## 其他观察

- `chkstatus` 返回的 `ss4` 字段（代码用作 `wlan_user_mac`）**不稳定**：
  连续 6 次调用中 5 次返回 `000000000000`、1 次返回真实 MAC。
  这与浏览器抓包值 `000000000000` 一致，且服务端以 IP 为主键，不影响登录。
- 服务端自述 `ep_http_port=801`，而代码配置用 `803`。实测 803 可用，
  程序已在 `test` 子命令中提示该差异。
