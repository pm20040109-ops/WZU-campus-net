# 设备数限制机制调查（2026-09-20）

**问题**：账号只能同时在线两台，实际本应更多。

**结论**：这不是客户端的算法，而是**服务端维护的「账号 → 已绑定 MAC」表**。
上限值存在学校的 AAA/Radius 上，客户端既看不到也改不了。
改 `terminal_type` / 前缀 / `mac_type` 都**不能**增加可用台数。

---

## 一、直接证据：`mac/find` 接口

这是本次调查最关键的发现。页面用 `page.portal_api + 'mac/find'` 查询本账号的终端列表，
**只读**，可直接调用（本节所有数据来自该接口，未做任何写操作）：

```
GET http://192.168.0.203:803/eportal/portal/mac/find?callback=dr1002
    &login_method=0&find_mac=0&user_account=<学号>
    &wlan_user_ip=<ip转整数>&wlan_user_mac=<mac>&jsVersion=4.5.1&v=1&lang=zh
```

实测返回（连续多次采样一致）：

```json
{"result":1,"msg":"查询MAC地址成功！","list":[
  {"online_session":27924,"online_ip":"10.99.y.y","online_mac":"6e1122334402",
   "phone_flag":"1","is_bind_mac":"1","is_perceive":"0","online_time":"2026-09-20 12:09:29"},
  {"online_session":28377,"online_ip":"10.99.x.x","online_mac":"8c1122334401",
   "phone_flag":"0","is_bind_mac":"1","is_perceive":"1","online_time":"2026-09-20 12:10:56"}
]}
```

`list` 长度就是**当前占用的台数 = 2**，与"只能两台"完全吻合。
两条记录的 `is_bind_mac` 均为 `1`，说明它们是**已绑定的 MAC**，不是临时会话。

字段含义：

| 字段 | 含义 |
|---|---|
| `online_session` | 会话号 |
| `online_ip` / `online_mac` | 该终端在网关侧的真实 IP / MAC |
| `phone_flag` | `1`=移动端，`0`=PC —— 与页面账号前缀 `,1,` / `,0,` 一一对应 |
| `is_bind_mac` | 是否为已绑定的 MAC |
| `is_perceive` | 是否通过无感知登录 |

## 二、登录被拒时的服务端返回

页面 `a40.js` 的登录成功回调里有这样一条分支（按顺序排在 `self_auth_url`、
`apg_data` 之后）：

```js
else if (typeof(json.over_mac_list) != 'undefined' && json.over_mac_list.length > 0) {
    $('input[name=0MKKey]')[0].attr('disabled', false);
    loginverify.show_unbind_box(json.over_mac_list);
    return false;
}
```

`show_unbind_box` 弹出的正是一张终端表格，标题为 **「账号已超出最大登录数」**，
每行显示 序号 / IP地址 / MAC地址 / 上线时间 / 操作，操作列是「下线」或「解除绑定」。

也就是说：**超限判定完全在服务端**。服务端认为超限时，把 `over_mac_list`
（当前占用的终端清单）返回给页面，页面只负责展示和提供解绑入口。

## 三、客户端的角色：只决定「归入哪一类槽位」

`a40.js` 里 `user_account` 的构造：

```js
accountPrefix = (term.accountPrefix == 1
    ? ((term.type == 2) || (ipad_terminal_identity == 1 && (term.type == 3 || term.type == 4))
        ? ',a,'   // 移动端/平板
        : ',0,')  // PC            ← customPerceive == 1 时这组变成 ',a,' / ',`,' 见下
    : '') + account;
```

原始字节里一共有 4 个字面前缀：`,0,` `,1,` `,a,` `,` ,`（反引号是模板占位符）。
两个分支由 `term.customPerceive` 选择，而 `loadConfig` **没有** `custom_perceive`
字段，默认走 `0`，即 PC=`,0,`、移动=`,1,`。我们的抓包值
`user_account=%2C0%2C<学号>` = `,0,<学号>` 与此完全吻合。

客户端参数（`terminal_type`、`mac_type`、`R6`、账号前缀）的作用是告诉 AAA
**这个新会话属于哪一类终端**，从而匹配到对应的绑定槽位。
它们**不能**让绑定表多出一条记录 —— 所以改这些值不会变出第 3 台。

`loadConfig` 与页面 JS 中**没有**任何"最大设备数/最大并发数"字段
（已逐一核对 85 个字段）；客户端也没有任何计数逻辑
（`onlineCount`/`deviceCount`/`terminalCount` 均 0 次出现）。

## 四、我们的程序不会额外占用槽位

页面在 `chkstatus` 返回全 0 MAC 时会用绑定列表回填真实 MAC：

```js
term.mac = (term.mac == '000000000000' || term.mac == '111111111111')
           ? macList[i].online_mac : term.mac;
```

我们的程序没有这个回填，直接上送 `wlan_user_mac=000000000000`。
但实测多次调用 `mac/find`，本机条目始终稳定为
`online_mac=8c1122334401, session=28377`，**未产生"未知设备"新条目** ——
说明网关侧有 ARP/DHCP 表，按 IP 就能关联到真实 MAC，不依赖客户端上送。

**所以反复重连不会累积占用设备数。**

## 五、想腾出位置，只有两条正规途径

1. **浏览器自助**：打开 `http://192.168.0.203/`，登录时若被拒会弹出终端表格，
   点对应行的「下线」或「解除绑定」即可。
   （对应接口 `login_verify/unbind`，**这是写操作**，本项目未调用。）
2. **学校自服务系统 / 网管**：真正的上限值配在 AAA/Radius 上，只有管理员能改。

> 本项目**未实现**自动解绑功能：那属于写操作，会强制踢掉用户其它设备，
> 风险与副作用都超出"自动登录"的范畴。如确有需要，建议走上面第 1 条手动操作。

## 六、`un_bind_mac` / `find_mac` 的实测值

| 字段 | 实测值 | 说明 |
|---|---|---|
| `un_bind_mac` | `0` | 未开启"禁止绑定 MAC" |
| `find_mac` | `0` | 未启用强制 MAC 查找 |
| `check_online_method` | `0` | 未启用无感登录的在线校验 |
| `enable_uuid` | 字段不存在 | 无感登录 uuid 未启用 |

页面里另有一套**无感登录 uuid 指纹**（`deviceUuidExecute`，采集 CPU 核心数、
内存、平台、触摸支持、屏幕分辨率、时区、Canvas/WebGL 指纹等 27 项），
但其启用条件是 `enable_uuid == 1 && checkOnlineMethod == 1`，当前均不满足。
它的用途是**识别"是不是同一台设备"**，而不是限制数量。
