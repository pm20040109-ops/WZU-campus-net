# 关于「绕过两台设备限制」的结论（2026-09-20）

> 公开整理说明：设备地址使用保留 U/L 位差异的合成示例，原始个人标识不在当前文档展示。


**问题**：能否绕过"同时在线两台"的限制？

**结论**：**不能，而且这不是能力问题——是不存在这样的技术路径。**
限额不在客户端，客户端也没有任何能让服务端多记一条的输入。

> 本文只做**只读**取证（`chkstatus` / `loadConfig` / `mac/find` / `online_list`
> / 页面 JS 分析 + 端口连通性探测）。没有修改本机 MAC、没有调用任何写接口、
> 没有实施任何绕过行为。未决与建议部分在文末。

---

## 一、为什么"绕过"在架构上不可行

### 限额在服务端，客户端看不到也碰不到

逐一核查了客户端能接触到的所有配置面：

| 面 | 结论 |
|---|---|
| `loadConfig` 全部 **85 个字段** | **无任何**数量上限配置项 |
| 页面 JS 全部字号/常量扫描 | `maxLogin` / `deviceLimit` / `concurrent` 等关键字**零命中** |
| 登录请求全部 17 个参数 | 无一能影响绑定表条数 |

服务端维护的是一张 **`账号 → 已绑定 MAC`** 表，表长就是占用的名额数。
这份数据**只存在于网关/AAA(Radius) 侧**，客户端拿到的只是它的一个只读投影。

### 客户端只能"减"，不能"增"

页面里唯一有写能力的接口是解绑：

| 接口 | 作用 |
|---|---|
| `mac/find`、`online_list` | **读**：列出本账号终端 |
| `login_verify/unbind` | **写**：下线 / 解除绑定 —— 只减少条数 |
| `mac/unbind` | **写**：同上 |

没有任何"新增槽位""扩容""替换设备"类接口。
登录成功只是**占用**已有槽位，不会创建新槽位——这一点已实测：
反复重连时 `mac/find` 里的 `online_session` 保持不变，条数恒为 2。

### 伪造 MAC 这条路是死的（我最初的猜想，已被实测推翻）

这是我原本认为最有可能的突破口，但**验证下来不成立**：

页面里 `term.mac` 确实有三条**客户端可控**的回填路径：
```js
term.mac = util.getQueryString('wlanusermac');   // URL 参数
term.mac = cookie.get("mac");                     // Cookie
term.mac = macList[i]['online_mac'];              // 绑定列表回填
```
且 `wlan_user_mac` 就是登录请求的一个普通参数，改起来并不难。
**但**：我们的程序长期上送 `wlan_user_mac=000000000000`，
服务端却始终把它正确关联到真实 MAC（`00:00:00:00:00:01`），
且从未产生"未知设备"条目。

**说明网关以自己的 ARP/DHCP 表为准，不采信客户端声明的 MAC。**
所以伪造 MAC 既不能新增槽位，也不会被记成新设备。

> 补一句：假设哪天服务端改成采信客户端 MAC，那也不是"绕过"，
> 而是把**别人**的设备顶掉——会命中 `case 2: 该账号正在使用中`，
> 或触发 `over_mac_list` 让人家来解绑。本质是**踢人**，不是扩容。
> 这种伤害他人的操作我不做。

### 更换身份标识也无效

有人会想到改 `terminal_type` / 账号前缀（`,0,` `,1,` `,a,`）来"装成不同设备"。
实测与代码分析表明：这些参数只决定**新会话归入哪一类槽位**
（PC 槽 / 移动槽），**不会增加绑定表条数**。上限是表长，不是分类数。

## 二、那"两台"到底是什么

学校在 AAA/Radius 上给该账号配的**并发会话数上限**。
门户页面把它显示为"账号已超出最大登录数"，但**没有任何修改入口**——
`_self` 自服务只提供四项：`0=认证` `1=免登录` `2=改密码` `3=绑定运营商`，没有"设备管理"。

端口探测确认也没有独立的自助服务站点（`192.168.0.203` 上仅 80/801/802/803 开放，
均为同一套 Dr.COM 门户；8080/8443/9090 等常见自服务端口不通）。

**唯一能改这个数的人是学校的网络管理员。**

## 三、能合法改善现状的三件事

虽然不能"绕过"，但下面这些能实际解决"名额被占满"的困扰：

### 1. 关闭手机的「私有 Wi-Fi 地址」（最有效，立刻可做）

这是前一份文档查明的根因：绑定表以 MAC 为键，而你这台手机的 MAC 是
**随机化**的（第 1 字节 `0x02`，LAA 位置位）。系统每重置一次地址，
服务端就多记一台"设备"，旧记录还不清——**你在自己吃自己的名额**。

- **iOS**：设置 → 无线局域网 → 该网络右侧 ⓘ → 关闭「私有无线局域网地址」
- **Android**：该网络 → 隐私（或高级）→ 选「使用设备 MAC」
- **Windows**：设置 → 网络 → 该 Wi-Fi → 关闭「随机硬件地址」

关掉之后 MAC 固化，重连不再累积占位。这是**唯一能自己解决**的一条。

### 2. 清掉僵尸绑定

名额已被占满时，用浏览器打开 `http://192.168.0.203/`，
登录被拒时会弹出终端表格，逐条「下线」/「解除绑定」把旧记录清掉。

本项目**不提供**自动解绑功能：那属于写操作，会强制踢掉你其它设备，
且需要提交账号密码到解绑接口，风险与"自动登录"不是一个量级。
手动操作一次只需十几秒，更稳妥。

### 3. 找网管提额（真正的解决办法）

如果确实需要更多设备同时在线（比如手机 + 笔记本 + 平板），
这就是**合理需求**，直接联系网络中心申请提高并发数上限即可。
很多学校对高年级/研究生本身就有更高配额。

## 四、未决问题

**限额是全局 2 台，还是分类配额（如 PC 1 + 移动 1）？**

当前占用恰好 `1 PC + 1 移动 = 2`，两个模型都能解释，现有数据无法区分。
区分方法（需要你配合操作，脚本无法完成）：

- 用**第二台 PC** 登录
  - 成功 → 全局上限 2
  - 被拒且提示超限 → 分类配额，PC 名额已满

这个结果会决定：如果你主要用 PC，提额申请该怎么说。

---

## 五、我把边界说清楚

- 本文没有实施、也没有提供任何绕过手段，因为**技术上不存在**：
  限额与绑定表都在服务端，客户端只有只读投影和一个"减少条数"的写接口。
- 即使存在可利用点（例如服务端将来改为采信客户端 MAC），
  其效果是**顶掉他人设备**而非扩容，且会用到账号密码调用解绑类接口。
  这类越权/伤害他人的操作我不会做。
- 如果你的真实诉求是"我的设备老被踢"或"名额被莫名占满"，
  第 1、2 条能直接解决；如果是要**合法提高上限**，第 3 条是正路。
  这三条我都可以继续帮你深入（例如写个`mac/find` 只读查询小工具，
  方便你随时看自己占了几台）。
