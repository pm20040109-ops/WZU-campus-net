# 设备数限制机制的缺陷分析（2026-09-20）

> 公开整理说明：设备地址使用保留 U/L 位差异的合成示例，原始个人标识不在当前文档展示。


配套文档：`设备数限制机制-20260920.md`（机制本身）。
本文分析**这套设计的问题**，重点是解释"为什么名额会被莫名占满"。

> 调查全程**只读**：仅调用 `chkstatus` / `loadConfig` / `mac/find` / `online_list`。
> 未调用 `login_verify/unbind`、`mac/unbind`、`logout`、`login` 等任何写操作。

---

## 核心缺陷：用 MAC 当设备身份键

### 问题

绑定表以 **MAC 地址**为唯一键，每条记录 = 一台"设备"。上限（实测 2）就是允许的
记录条数。但 MAC 在现代终端上**不再稳定**：

| 场景 | MAC 是否变化 |
|---|---|
| iOS 14+ / Android 10+ / Win10+ 默认开启「私有 Wi-Fi 地址」 | **每 SSID 随机** |
| 用户手动关闭/重置该功能 | **变化** |
| 系统重装、网卡更换、虚拟网卡 | **变化** |
| USB 网卡 / 扩展坞 / 手机热点共享 | **变化** |

每次 MAC 变化，服务端就把它当成**一台新设备**，占用一个新名额。
旧记录若未及时清理，名额就被"僵尸"占住 —— 用户手里只有两台设备，
却提示"已超出最大登录数"。

### 实测证据

`mac/find` 返回的两条记录：

| MAC（示例值） | 第 1 字节 | LAA 位 | 类型 | phone_flag |
|---|---|---|---|---|
| `02:00:00:00:00:01` | `0x02` = `00000010` | **1** | **随机化 MAC** | 1（移动端） |
| `00:00:00:00:00:01` | `0x00` = `00000000` | 0 | 厂商固化 MAC | 0（PC） |

> 上表 MAC 已替换为示例值，但**第 1 字节与 LAA 位保持了原值的语义**：
> 示例首字节分别为 0x02 和 0x00，两者 LAA 位分别是 1 和 0。

IEEE 802 规定第 1 字节 **bit1 = 本地管理位（LAA）**：置 1 表示该地址由软件生成，
即"私有/随机 MAC"。移动端那条正是 LAA=1 —— 说明这台手机开着「私有 Wi-Fi 地址」。

**这就是缺陷的直接证据**：身份键选用了会被终端主动随机化的字段。
用户什么都没做，只要系统重置一次私有地址，就凭空多出一台"设备"。

对比：PC 那条是厂商固化 MAC（LAA=0），所以身份稳定 ——
本项目反复重连也只占同一个名额（已实测确认 session 号不变）。

### 附带问题：MAC 由客户端上送

`wlan_user_mac` 是登录请求的一个普通参数，页面里有**三条客户端可控的回填路径**：

```js
// (a) 网关注入的 query string
if (util.getQueryString('wlanuserip') && util.getQueryString('wlanusermac')) {
    term.ip  = util.getQueryString('wlanuserip');
    term.mac = util.getQueryString('wlanusermac');   // 可被 URL 覆盖
}
// (b) cookie
if ((term.mac == '000000000000' || term.mac == '111111111111') && cookie.get("mac")) {
    term.mac = cookie.get("mac");                     // 可被 cookie 覆盖
}
// (c) mac/find 返回的绑定列表回填
term.mac = (term.mac == '000000000000' || term.mac == '111111111111')
           ? macList[i]['online_mac'] : term.mac;
```

若服务端直接采信这个值建立绑定，则身份可被任意伪造。
**好消息**：实测表明网关侧另有 ARP/DHCP 表 —— 我们的程序上送
`wlan_user_mac=000000000000`，服务端仍正确关联到真实 MAC
`00:00:00:00:00:01`，且多次调用未产生"未知设备"条目。
所以这一条**在本校当前配置下未被利用**，但属于协议设计上的信任边界隐患。

## 缺陷二：学校自己的页面上有个 JS bug

`a40.js` 中：

```js
if (page.enable_login_verify == 2 && error_msg.indexof('In use')
    && typeof(loginverify) !== 'undefined') { loginverify.find_mac(); }
```

**两处问题**：

1. **拼写错误**：`.indexof` 小写。JS 里方法名是 `indexOf`，`.indexof` 是
   `undefined`，调用它会抛 `TypeError`。
   全文件 `.indexOf(` 出现 **144 次**，`.indexof(` 仅此 **1 次** —— 明显是笔误。

2. **逻辑也反了**：即便拼对，`indexOf` 未找到返回 `-1`，而 `-1` 是**真值**，
   条件恒成立。正确写法应为 `indexOf('In use') > -1` 或 `includes('In use')`。

**当前影响**：`enable_login_verify` 实测为 `0`（页面注释：「0不启用 1认证前 2认证后」），
因短路求值这段代码不执行，所以暂时不发作。
**但**：学校一旦把它改成 `2`，"账号被占用时自动弹出终端列表"这个自助功能会直接报错失效 ——
用户被拒绝登录，却看不到任何可操作的界面。这属于**埋着的坑**。

## 缺陷三：限额与占用量对用户完全不可见

- 页面上"最大登录数"文案只出现 **1 次**，且只在**已被拒绝之后**才显示。
- 用户无法预先知道：上限是几台、自己已占几台、是哪个设备占着。
- `mac/find` 只返回**当前在线**的终端；**已绑定但已离线**的设备不在其中
  （已验证：两条记录的 `time_long` 都随时间增长，说明都是真在线，没有可观测的离线条目）。
  所以**连查询接口都无法告诉你"僵尸绑定"占了多少**。

结果：用户看到"超出最大登录数"时，弹窗里可能只列出一两台设备，
与"我已经关掉其他设备了"的认知冲突，却找不到原因 —— 真正占位的那条记录不在列表里。

---

## 缺陷四：`enable_login_verify=0` 让自助入口形同虚设

三个取值（页面注释）：`0` 不启用 / `1` 认证前 / `2` 认证后。
实测为 **0**，意味着正常登录流程**不会**主动做并发校验、也不会主动提示查看终端列表。

用户只能等被服务端拒绝（返回 `over_mac_list`）才看到解绑界面。
**建议**：把 `enable_login_verify` 设为 `2` 并**修掉上面那个 `indexof` bug**，
让用户在登录前就能自查设备列表。

---

## 关于查询接口的一个安全优点

`mac/find` 的 `user_account` / `wlan_user_ip` 参数**会被服务端忽略**，
服务端按**请求源 IP** 反查账号。实测：把 `user_account` 换成不存在的
`000000000000`、或把 IP 换成 `1.2.3.4`，返回的都仍是我自己的终端列表
（用不存在的账号做的探测，未查询任何他人数据）。

**这是好事**：无法通过篡改参数越权查看他人设备。属于设计上的正确取舍。

## 未决问题

**限额是全局 2 台，还是分类配额（如 PC 1 + 移动 1）？**

当前占用恰好是 `1 PC + 1 移动 = 2`，两个模型都能解释，现有数据无法区分。

区分方法（需真实设备，不是脚本能做的）：
再让**第二台 PC** 登录 ——
- 成功 → 全局上限 2
- 被拒并提示超限 → 分类配额，PC 名额已满

## 结论与建议

| 缺陷 | 性质 | 影响 | 可缓解性 |
|---|---|---|---|
| MAC 作身份键 | **设计缺陷** | 随机化 MAC 导致名额被虚占 | 需校方改绑定策略（改用账号+设备指纹，或放宽上限） |
| MAC 由客户端上送 | 信任边界隐患 | 理论上可伪造身份 | 网关有 ARP 表兜底，当前未被利用 |
| `indexof` 拼写 bug | 实现 bug | `enable_login_verify=2` 时自助功能失效 | 校方改一行 |
| `indexOf` 逻辑取反 | 实现 bug | 同上，条件恒真 | 校方改一行 |
| 限额不可见 | 可用性缺陷 | 用户无法自查、无法定位占位设备 | 校方开启 `enable_login_verify=2` |
| 离线绑定是否占位 | **未确认** | 若是，则名额会被永久占死 | 需在设备离线后复测 |

**给用户的可操作建议**：

1. **关闭手机的「私有 Wi-Fi 地址」**（iOS：设置 → 无线局域网 → 该 SSID 的 ⓘ →
   关闭"私有无线局域网地址"；Android：该网络 → 隐私 → 使用设备 MAC）。
   这是最有效的一条 —— 能让身份键稳定下来，避免自己吃掉自己的名额。
2. 换设备/重装系统后，若提示超限，用浏览器打开 `http://192.168.0.203/` 登录，
   被拒时会弹出终端列表，点「下线」腾出名额。
3. 本校 PC 侧用的是厂商 MAC，本项目反复重连不会累积占用，这一点已实测确认。
