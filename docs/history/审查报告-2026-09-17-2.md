## 二、本轮新发现问题

### P1-1 该项目目录已是「运行中的生产安装」，凭据文件无法靠删除根治

- 位置：`campus-login/dist/campus_login.json` + 注册表 + 运行中进程
- 实测事实（三份证据）：

| 证据 | 内容 |
|---|---|
| 文件 | `dist/campus_login.json` 含真实学号与**明文密码**，且 `auto_login_on_start=1`、`auto_watch=1` |
| 注册表 | `HKCU\...\Run\CampusNetLogin` = `"...\campus-login\dist\CampusNet.exe" --minimized` |
| 进程 | PID 20516（引导器）/ 20592（主进程），命令行 `--minimized`，启动于今日 11:11:54，**此刻仍在运行** |

- 上一轮只把该文件定性为「发布目录内残留」并建议「发布前删除」。本轮发现这个定性**不完整**：
  1. 该目录不是待发布的副本，而是**开机自启指向的实际安装位置**（注册表路径就在 `campus-login\dist\`）；
  2. 该 exe 运行时 `CONFIG_PATH = exe 所在目录`，因此 `dist/campus_login.json` 是**当前生效的生产配置**；
  3. 因此**单纯删除不具备持久性**——只要用户再点一次 GUI 的「保存账号设置 / 保存服务器设置 / 保存并应用」，`_save_account`（`campus_gui.py:799`）、`_save_network`（`827`）、`_save_auto`（`836`）都会调用 `cl.save_config(cfg)` 把凭据**原样写回 dist**。
- 影响：
  - 整体拷贝/压缩该目录分享给同学，即泄露凭据**且附带开机自启的可用安装**（比上一轮描述的更严重）；
  - 删除文件无法解决，下次保存即复现。
- 建议：这不是「清理一个残留文件」的问题，而是**配置存放位置需要一次决策**：
  - 方案 A（推荐）：把 exe 模式配置改到 `%APPDATA%\CampusNet\campus_login.json`，源码目录与发布目录都不再承载凭据；
  - 方案 B：接受配置随 exe 同目录，但发布前必须**移出整个 dist 目录**（而非只删 json），并同步清理注册表自启项。
- 处置需用户确认（涉及删文件 / 改注册表 / 停进程，均未擅自执行）。

### P2-1 `check_internet` 异常捕获漏掉 `http.client.HTTPException`，三个 CLI 入口直接崩溃

- 位置：`campus_login.py:464-472`
- 现状：只捕获 `urllib.error.HTTPError` 与 `(urllib.error.URLError, OSError)`。
- 关键事实：`http.client.HTTPException` **不是 `OSError` 的子类**，实测：
  ```
  http.client.BadStatusLine          URLError=False  OSError=False
  http.client.IncompleteRead         URLError=False  OSError=False
  http.client.LineTooLong            URLError=False  OSError=False
  ```
- 实测复现（本地伪造返回非 HTTP 内容的服务端，模拟网关/运营商劫持）：
  ```
  cmd_status  -> !!! 未捕获异常 BadStatusLine: GARBAGE NOT HTTP
  cmd_login   -> !!! 未捕获异常 BadStatusLine: GARBAGE NOT HTTP
  cmd_test    -> !!! 未捕获异常 BadStatusLine: GARBAGE NOT HTTP
  ```
- 调用点分布（`check_internet` 共 5 处，其中 3 处在 `try` 之外）：

| 位置 | 是否被 try 覆盖 |
|---|---|
| `cmd_login:515` | 是 |
| **`cmd_login:524`** | **否** |
| **`cmd_status:541`** | **否** |
| `cmd_watch:566` | 是 |
| **`cmd_test:604`** | **否** |

- 影响：双击 `3-查状态.bat` 的用户拿到的是一段 Python 原始 traceback（且在 `chcp 65001` 下更不易读），而不是可读的状态行。GUI 不受影响（`_task_refresh` 用 `except Exception` 兜住）。
- 与上一轮的关系：上一轮修的是「被劫持返回 200 被误判 online」，本轮是**同一函数的异常分支**——劫持方返回非 HTTP 字节时反而绕过全部处理。修复只做了一半。
- 建议：捕获元组放宽为 `(urllib.error.URLError, OSError, http.client.HTTPException)`，或直接 `except Exception: continue`（该函数语义就是「探测失败就换下一个 URL」）。

### P2-2 `load_portal_config` 局部成功时把 `enable_r3` / `en_md5` / `login_method` 静默降级为 0

- 位置：`campus_login.py:285-293`
- 事实：三个字段用的是 `int(d.get(x) or 0)`，**与 `program_index`/`page_index`/`rcn` 的 `d.get(x) or result[x]` 写法不一致**——后者会保留兜底值，前者不会。实测（注入不同形态的 loadConfig 响应）：

| 响应形态 | enable_r3 | 期望（兜底值） |
|---|---|---|
| 完整响应 | 1 | 1 ✅ |
| **省略 enable_r3** | **0** ❌ | 1 |
| 省略 en_md5 | 0 | 0（巧合一致） |
| 省略全部三个 | **0** ❌ | 1 |

- 影响：`enable_r3` 在 `do_login` 中直接决定上送 `enable_r3=0`（`:367`）——页面语义为「串接 pppoe 代拨 0 停用 1 启用」（`reference/a41.js` 注释确认）。一旦学校接口在某个时段返回的 `data` 里缺这个键（字段裁剪、灰度、降级响应），程序会**静默按停用代拨登录**，表现为能连但行为不符预期，且日志里那句「已获取门户配置」照常打印，毫无线索。
- 建议：与相邻三行统一写法，或先 `result.update(...)` 再逐字段回填兜底。

### P2-3 配置只校验「顶层形状」，不校验「值类型」——上一轮 P3-1 的同类问题另一半

- 上一轮 P3-1 测的是顶层形状（`5` / `[1,2]` / `null`）。本轮发现**值类型**同样无防护，且后果不同（不报「配置读取失败」，而是伪装成网络故障或直接崩溃）：
  1. **`timeout` 为字符串**（JSON 合法，如手动编辑或外部工具改写）：
     ```
     loaded timeout = '5' (str)
     check_status   -> TypeError: 'str' object cannot be interpreted as an integer
     cmd_status 输出: [错误] 无法连接认证服务器(192.168.0.203): 'str' object cannot be interpreted as an integer
     ```
     真实原因是配置类型错，报出的却是「无法连接认证服务器」→ 误导用户去查网线。
  2. **`watch_interval` 非数字** → `cmd_watch:561` 的 `max(10, int(...))` 位于 `try` 之外，**直接崩溃**（实测 `ValueError: invalid literal for int()`）。GUI 侧 `_task_watch:729` 同样取值，异常逃出线程函数，`finally` 只补发 `watch=False`，窗口无任何提示。
  3. **GUI 启动即失败**：`campus_gui.py:169` / `:171` 的 `int(cfg.get("auto_login_on_start", 0))` 在 `__init__` 中、无任何保护。实测 `"abc"` / `""` → `ValueError`，`None` → `TypeError`。**`--windowed` 打包后无控制台，进程会静默消失**——正是 README L109「exe 启动闪退」那条，但 README 归因为「缺 json / 缺图标 / 杀软」，真实成因之一在这里。
- 建议：`load_config` 出口做一次类型规整（`timeout`/`watch_interval`/`drcom_port`/`eportal_port` 强制 int 并夹取范围，失败则回退默认并 `err()` 提示），一处修复覆盖 CLI 与 GUI 全部调用点。

### P2-4 注销与守护互相抵消：用户主动注销后 ≤ 守护间隔秒被自动重新登录

- 位置：`campus_gui.py:665-672`（`logout_click` / `_task_logout`）与 `724-762`（`_task_watch`）
- AST 精确边界确认：`_task_logout` 与 `logout_click` **均不含任何 `watch_stop` 引用**，而 `_task_watch` 的掉线分支调用 `cl.do_login`。
- 时序：
  1. 守护运行中（`watch_stop` 未置位，循环存活）；
  2. 用户点「注销下线」→ 仅做 `busy` 冲突检查，不停守护；
  3. `do_logout` 成功 → 网络断开；
  4. 守护线程下一轮 `check_internet` → offline → `do_login` → **自动重新认证**。
- 影响：用户明确表达的「下线」意图在 `watch_interval`（默认 30 秒）内被程序自行推翻，且日志里只留下「[守护] 互联网不通…尝试重新登录…重连成功」，看起来像正常运行。想真正下线必须手动停守护 + 注销两步，界面无任何提示。
- 建议：注销成功后自动停守护，或注销前 `messagebox` 提示「守护运行中，注销后 30 秒内将自动重连，是否先停止守护？」。

### P2-5 GUI `_poll` 的 handler 异常会**永久切断事件泵**（上一轮评级偏低）

- 位置：`campus_gui.py:458-477`
- 结构（关键在第 477 行）：
  ```python
  def _poll(self):
      try:
          while True:
              kind, payload = self.q.get_nowait()
              handler = {...}.get(kind)
              if handler is None:
                  continue
              handler(payload)          # ← 在 try 内
      except queue.Empty:           # ← 只捕 queue.Empty
          pass
      self.root.after(150, self._poll)   # ← 在 try/except 之外
  ```
- 实测：让任一 handler 抛异常 → `RuntimeError` 逃出 `_poll` → **`after()` 不再注册**，队列积压但再无消费者。
- 上一轮把同类场景评为「概率低、后果轻（回调内异常）」。本轮实测认为**后果被低估**：一旦触发，界面**永久失去日志、状态刷新与全部托盘响应**（托盘菜单点击仍会 `_qput`，但没人再取），且 `--windowed` 下连 stderr 都没有，用户只看到「点了没反应」。触发路径真实存在——`_real_quit` → `root.destroy()` 之后（由 `_on_tray_cmd` 在 `_poll` 内部触发），while 循环仍会继续消费队列，实测对已销毁控件调 `config()` 抛 `TclError: invalid command name ".!button"`。
- 建议：两行修复——把 `handler(payload)` 单独包 `try/except Exception: pass`，并把 `self.root.after(...)` 放进 `finally`。

### P3 级

- **P3-1 `md5_plus` 与页面算法不符，且 `R2` 未随 `en_md5` 联动。** 页面（`reference/a40.js`）为 `upass=calcMD5(PID+upass+CALG)+CALG+PID` 并同时置 `R2=1`；代码 `md5_plus`（`:624-627`）是裸 `hashlib.md5(password)`，且 `params["R2"]` 恒为 `""`（`:350`）。当前 `en_md5=0` 不触发，注释也写明「不会走到这里」，但这是**一条一旦学校开启 MD5 就会静默送错密码**的预留分支——它看起来像已实现，实际不可用。
- **P3-2 `--server` / `--drcom-port` / `--eportal-port` 被接受但静默忽略。** `common()` 把这三个选项挂到了 `status`/`logout`/`watch`/`set` 四个子命令，但 `main()`（`:659-681`）只在 `cmd_set` 分支消费；`cmd_login`/`cmd_status`/`cmd_logout`/`cmd_watch`/`cmd_test` 全部读 `cfg`，实测 `args.server` 在 `main()` 中出现 **0** 次。更不一致的是 `test` 与 `login` 子命令**不接受**这三个选项（argparse 直接报错）。用户 `python campus_login.py status --server 10.0.0.1` 会得到旧服务器的结果而无任何警告。
- **P3-3 `_task_auto_login` 末次重试后仍 `sleep(10)` 且文案误导。** `:685-710`，循环 `range(1,7)` 共 6 次；第 6 次失败仍打印「(10 秒后重试 6/6)」并再睡 10 秒，但不存在第 7 次。上一轮修掉了 `do_login` 的同类问题（`if attempt < 3`），此处遗漏。
- **P3-4 并发 `do_login` 无互斥。** `_task_auto_login` 与 `_task_watch` 都不置 `self.busy`（AST 确认），可与用户点击的 `_task_login` 并发进入 `do_login` / `load_portal_config`。叠加 P3-5 的重复请求，弱网下会放大认证内核的「clientip online」类拒绝。
- **P3-5 一次 `do_login` 打两次 `chkstatus`。** `do_login:313` 查询一次，`load_portal_config:265` 内部又查一次（且异常被吞）。总请求数 1+2+1=4 次，其中一次纯冗余。
- **P3-6 README 三处与实现不符（且自相矛盾）。**
  - L55「首次会自动加载/创建 `campus_login.json`」与 L84「首次启动自动建默认配置」——实际 `load_config`（`:125-133`）**只读不写**，无文件时仅返回 `DEFAULT_CONFIG` 副本；`save_config` 只在用户点保存时调用（CLI 2 处 / GUI 3 处，均非启动路径）。实测确认 GUI 启动路径不含 `save_config`。
  - L109「exe 启动闪退：通常是缺 `campus_login.json`」与上述「无需附带、自动创建」直接冲突。
  - 真实语义是：缺 json **不会闪退**，只是账号为空导致登录失败；而闪退另有真因（见 P2-3.3）。
- **P3-7 托盘不可用 + 守护运行时，窗口无法退出。** `_on_close`（`:864-869`）：守护存活 → `_minimize_to_tray()`；`_minimize_to_tray`（`:585-596`）在 `_ensure_tray()` 失败时退化为 `root.iconify()` 并 `return`，**不置 `hidden_in_tray`**。此时点 X 只会最小化到任务栏，既无托盘菜单可「退出程序」，关窗也退不出。实测本机托盘可正常初始化（`LoadImageW` 返回有效句柄），故仅在 `TrayIcon` 导入失败 / 创建超时的机器上触发。
- **P3-8 `Referer` 多带 `:80`。** `cfg_server_of`（`:165-170`）取 URL 的 host:port，drcom 请求因此发送 `Referer: http://192.168.0.203:80/`，抓包值为 `http://192.168.0.203/`。实测服务端不校验，但属字节级保真偏差。
- **P3-9 eportal 端口硬编码 803，与服务端自述值不符。** `reference/loadConfig` 自述 `ep_http_port=801`、`ep_https_port=802`，代码 `DEFAULT_CONFIG["eportal_port"]=803` 且**从不读取** `ep_http_port`（实测源码中该键 0 次出现）。当前实网 803 可用（`test` 通过），属潜在脆弱点：学校若按自述端口调整，程序不会跟随。
- **P3-10 `user_agent` 参数的空格编码为 `+` 而非 `%20`。** 抓包为 `%20`，代码 `urlencode` 产生 `+`。二者服务端解码后同值，**非功能性缺陷**，仅记录以备将来排查。
