范围：`campus_login.py`、`campus_gui.py`、`tray_icon.py`、构建脚本、配置模板及 README；历史审查报告仅作对照。方法为源码检查和 Python 3.13.14 下的离线模拟，所有网络请求均由 mock 替代，使用虚构账号。未向校园网发送登录、注销或查询请求，未验证实际 exe、真实托盘故障及多 DPI 视觉效果。

## 1. [P2] 注销未等待后台登录任务结束，注销成功后仍可能重新上线

位置：`campus_gui.py:1073–1077`、`1093–1099`、`1153–1159`。

`logout_click()` 给守护线程设置 `watch_stop` 后立即启动注销线程，没有等待正在进行的探测或登录结束。守护线程只在循环入口检查停止事件；如果点击注销时它正等待 `check_internet()`，探测随后返回离线，仍会执行 `do_login()`。已经进入登录请求或重试阶段的任务也不会被该事件取消。

离线复现使用真实 Python 线程及同步事件：先阻塞守护探测，执行真实 `logout_click()`，等待模拟注销成功，再释放探测。观测到的调用顺序为：

```text
logout-ok -> login-after-logout
```

另一个入口是启动自动登录：注销没有设置 `auto_login_stop`，处于重试等待中的 `_task_auto_login()` 仍可继续认证。单独调用注销入口确认该停止事件保持未设置。

影响：用户明确选择下线，界面也记录注销成功，随后程序又自行登录。旧报告指出的问题已添加停止事件，但仍缺少并发时序保障。

建议：注销时同时取消自动登录和守护重试，在工作线程中等待已有认证操作结束，再执行最终注销；对登录/注销建立共同的串行执行机制。等待网络返回后、发起登录前及重试前应重新检查取消状态。不要在 Tk 主线程中等待网络任务。

## 2. [P2] 登录异常处理再次抛错，界面无法解除忙碌状态

位置：`campus_gui.py:1013–1025`，重点为 `1017–1023`。

当 `cl.do_login()` 抛异常时，处理器仅设置 `ok=False`，没有赋值 `msg`。后续失败日志访问 `msg`，触发 `UnboundLocalError`，于是 `dirty` 和 `done` 都未进入消息队列。`login_click()` 已设置的 `busy=True` 无法复位，登录、注销和测试按钮持续禁用。

复现一：令 `do_login()` 抛 `RuntimeError`，结果为 `UnboundLocalError`，队列只有一条日志，没有 `done`。

复现二：保留真实 `do_login()`，模拟返回 `{"result":0,"msg":9,"msga":123}`。响应处理的 `.strip()` 先抛异常，随后同样触发上述 GUI 二次异常。此例验证异常可沿现有函数路径传播，并非声称实际服务器返回过该数据。

建议：在异常分支赋值错误消息，将恢复状态的 `done` 通知放入 `finally`；配置加载也应放进受保护区域。

## 3. [P2] 托盘图标添加失败仍隐藏窗口，用户失去恢复入口

位置：`campus_gui.py:930–940`；`tray_icon.py:187–193`。

`_ensure_tray()` 成功仅表示托盘消息窗口已创建，不代表图标已成功添加。`TrayIcon.show()` 在 `Shell_NotifyIconW(NIM_ADD)` 返回失败时既不抛异常也不返回失败状态。而 `_minimize_to_tray()` 在调用 `show()` 之前就执行 `root.withdraw()` 并设置 `hidden_in_tray=True`，之后不检查 `tray.visible`。

离线验证：模拟 Win32 添加图标返回 0，真实 `TrayIcon.show()` 留下 `visible=False`；模拟该状态进入 GUI 最小化流程，主窗口仍被撤下，隐藏标志仍为真。没有操作真实托盘。

影响：在 Explorer 未就绪或添加图标失败时，窗口和托盘恢复入口同时消失；既有的“托盘不可用时退回任务栏”分支无法覆盖这一情况。

建议：让 `show()` 返回是否添加成功，先确认图标可见，再隐藏主窗口；失败时保留窗口或最小化到任务栏，并记录原因。

## 4. [P2] CLI 守护模式第一轮就丢弃命令行连接参数

位置：`campus_login.py:713–720`，相关入口 `884–890`。

`main()` 正确应用 `--server`、`--drcom-port`、`--eportal-port`，但 `cmd_watch()` 在第一次探测前就用 `cfg=load_config()` 替换整个配置。后续各轮也不重新叠加显式覆盖参数。

离线模拟以下命令的参数解析与守护执行：

```text
watch --server example.invalid --drcom-port 8080 --eportal-port 8081
```

传入守护函数的配置包含这些覆盖值，实际第一次探测使用的却是模拟磁盘配置中的 `192.168.0.203:80`、eportal `803`。没有真实请求。

影响：日志先声称临时覆盖生效，实际检测和重连却使用另一服务器或端口，与 README 的承诺不符。

建议：单独保存显式 CLI 覆盖，每轮先加载磁盘配置，再叠加覆盖项；未覆盖的字段继续支持热更新，不将临时参数写盘。

## 5. [P2] 联网探测把未知重定向当成功，也会被单个探测站故障误导

位置：`campus_login.py:602–616`，重点为 `612–616`。

当前 HTTP 异常分支有两条不可靠的推断：

1. 301/302/303/307 的 Location 只要不包含配置中的服务器字符串，就直接返回 `online`。认证页完全可能使用另一主机名或网关地址；收到重定向不等于已经验证公网连通。
2. 首个探测站返回 4xx/5xx 就直接返回 `offline`，不会尝试已配置的第二个站点。某一个站点的故障不等于本机断网。

离线结果：

| 模拟响应 | 实际结果 | 探测次数 |
|---|---|---:|
| 首站 302，Location 为另一域名的 `/login` | `online` | 1 |
| 首站 503，备用站预设可返回正确 Microsoft 内容 | `offline` | 1，备用站未调用 |

影响：第一种情况会让守护跳过必要的登录；第二种会触发无效的重连、错误状态和通知。GUI 在认证服务器仍显示在线时还可能反复提示“重连成功”。

建议：仅在满足预期状态码和内容时认定连通；未知重定向、单站 4xx/5xx 应继续检查备用目标，再根据所有结果区分离线与未知。已知认证重定向可以作为离线证据，但不应采用主机字符串子串匹配判断来源。

## 6. [P3] 纯 JSON 字符串包含括号时解析失败或返回错误层级

位置：`campus_login.py:285–299`，重点为 `290–296`。

`parse_jsonp()` 声明兼容纯 JSON，却无条件将全文第一个 `(` 当作回调锚点；这个括号可能处于 JSON 字符串值中。之后只从括号后查找对象起点，会错过真正的顶层对象。

离线复现：

```text
{"result":0,"msga":"failed (temporary)"}
  -> ValueError

{"result":1,"message":"ok (cached)","data":{"x":1}}
  -> 返回 {"x":1}，丢失顶层 result
```

影响限于纯 JSON 兼容路径；正常带回调的 JSONP 样例通过验证。建议先尝试解析完整 JSON 并验证对象类型，再进入 JSONP 包装解析。

## 7. [P3] MD5 兼容算法对非 BMP 字符与 JavaScript 不一致

位置：`campus_login.py:809–811`。

注释要求对每个 UTF-16 码元取低字节，但 Python `ord(ch)` 遍历的是 Unicode 码点。包含 emoji 等非 BMP 字符时，JavaScript 使用两个代理码元，当前实现却只产生一个字节。

使用虚构密码 `test` 加 U+1F600，与 `salted.encode('utf-16le')[::2]` 表示的 UTF-16 码元低字节计算结果比较，摘要不同。

影响条件为 `en_md5=1` 且密码含非 BMP 字符；项目说明中的当前学校配置为 `en_md5=0`，不影响该默认路径。建议按 UTF-16LE 码元低字节构造输入，并补充非 BMP 字符用例。
